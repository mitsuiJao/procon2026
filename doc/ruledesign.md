**方針**
- 入力は気温・湿度・降水量・生育ステージだけ。式やルールはこの範囲で動くものに絞る（葉面濡れセンサーは前提にしない。濡れは RH>=95% で代用）。
- 断定しない。出す／出さないの二択（`enabled`）。文言は「感染条件に該当」「閾値に近い」まで。「リスク高」「散布すべき」とは言わない。最終判断は生産者。
- 確度 A/B は記録用のメタ情報で、ロジックでは使わない。U（要確認）はデータに入れず、backlog 側に置く。
- 確度で足切りしない。晩腐病は重要度◎だが確度B。「A以上だけ」にすると現場で一番困る病害が消える。出すかどうかは `enabled` で決める。
- 農薬は確度ではなく「FAMICで登録確認済みか」で絞る。未確認の剤はデータに入れない。

**ルールの作り**
- 閾値ルールは `when`（all / any / not と、var・op・value の比較）。式モデルは `evaluator`（TS の関数名＋係数）。
- 両方あるときは `when` がゲート。`when` が真のときだけ `evaluator` を評価する（BOT-2 がこの形）。
- 式そのもの（Broome、Gubler-Thomas）は TS の関数、係数と閾値だけ YAML。式を YAML の DSL にすると膨らむので避けた。
- `eval` や `new Function` は使わない。条件の型は4種類で足りる。
- `level` は `when` だけのルールに必須（`near_threshold` / `conditions_met`）。`evaluator` のルールには書かず、`mid` / `high` で決める。
  - これは確認を取らずに進めた変更。戻したければ rules.yaml の先頭コメントとプロンプトを直す。
- 生育ステージは 0〜10 の順序値 1本（休眠期0、萌芽1、展葉2、開花直前3、開花4、落花直後5、幼果6、肥大7、着色8、収穫9、収穫後10）。
  - 「開花した／してない」の真偽値変数を増やさない。`stage >= 3` のように書く。
  - 「落花後20日」のような日数指定はステージ 5〜6 で近似。厳密にやるなら満開日からの日数を別変数で持つ（未実装）。
- 収穫まで何日かは、ルールでなく農薬の絞り込み側で使う（収穫前日数が残り日数を超える剤を候補から外す）。

**入力不足の扱い**
- 変数が取れないときは false ではなく null（判定不能）。false にすると「リスクなし」と誤表示される。
- all は、確実な false が1つあれば false。false がなく null があれば null。any はその逆。not は null のまま。
- 病害ごとにまとめるときの優先順位は conditions_met > near_threshold > undetermined > none。他ルールが none でも、1つでも undetermined があれば undetermined を返す。
- 画面では「入力不足のため未判定」を1行出す案を推している。ただしこれはまだ決まっていない。

**今のルール（10件）**
- 有効（A）: DM-1（べと病一次）、BOT-1（灰色かび病 Broome）、PM-1（うどんこ病 Gubler-Thomas）。
- 無効（B）: BOT-2、DM-2、RR-1、RR-2、ANT-1、ANT-2、RUST-1。
- 同じ病害で重なるもの（BOT-1/2、DM-1/2、ANT-1/2）は同時に成り立つことがある。画面には病害ごとに一番高いレベルだけ出す。

**A のルールの注意点**
- DM-1: 3-10 / 10-10-24 の簡易形。新梢10cm の条件は「展葉期以降（stage>=2）」で代用したので、原型とは一致しない。条件は日平均10℃以上・24hで10mm以上。
  - 出典は業界メディア（S037）と MDPI の論文（S036）。原典（Baldacci 1947）は未確認。
  - 依頼文の「べと病のミルズ式」は、実はリンゴ黒星病のモデル。べと病は 3-10 を使う。システム内の名称・出典は直す。
  - 「10/10/10」は民間サイト（S060）の表記で、3-10 と定義が違う。採用しない。
- BOT-1: logit = −2.647866 − 0.374927W + 0.061601WT − 0.001511WT²。T は 12〜32℃に丸め、40℃超は感染不適。濡れは RH>=95%、4時間超の乾燥でリセット。
  - 判定は 0.5 で注意、1.0 で該当。W=10,T=20 → −0.1209 / W=12,T=20 → 0.3845 / W=16,T=20 → 1.3952。
  - 出自はチリの生食用ブドウ（トンプソン・シードレス）。密着果房の欧州系品種では閾値調整がいるかもしれない。
- PM-1: 21〜30℃が6時間以上の日が3日連続で開始。以後、21.1〜29.4℃が6時間超の日は +20、それ以外は −10、最高35℃以上の日も −10。0〜100。
  - 状態を持つ（前日の指数に依存）ので、日次の指数を保存する仕組みがいる。
  - 開始日（3日連続の3日目か、翌日か）は文献であいまい。実装で選んで明記する。
  - 高温側の閾値は改訂研究（Peduto 2013）がある。`hotDayMaxC: 35` は今後見直す余地あり。カリフォルニアの乾燥した夏が前提のモデルなので、日本の梅雨期は他の病害との同時防除を優先。
  - 数値の裏取りは民間ブログ（S056）。APS の資料（S031）と整合はしている。

**B のルールの注意点**
- 雨量1mm、24hで10mm、連続2日、15〜20℃の冷雨などの閾値は、文献に根拠がない設計値。自園地のデータで調整する前提。
- B を A に昇格させていく過程がそのまま、Dコンの研究テーマになりうる。
- 除外したもの: Goidanich（原典の表が未入手）、Rossi 2008 の機構論モデル（入力が多い）、晩腐病の感染温度・濡れ時間（国内一次資料に数値なし）、灰色かび病の花期モデル（最適温度しか取れていない）。

**データの持ち方**
- ファイルが正（YAML）、コードは読むだけ。ビルド時に SQLite へ取り込む構成（取り込みは未実装）。
- 編集は開発者が YAML を書き換える。アプリ上の編集 UI は今回は作らない（追々やりたい）。
- 語彙を別ファイルに切り出した: diseases / stages / variables / frac / activeIngredients / frac_reclassified / sources。
  - 理由: 変数名を打ち間違えても黙って「未入力」扱いになり、永遠に判定不能になる。これが一番危ない。参照はすべて検証スクリプトで確認する。
  - ID は不変、名前は表示用。ID を変えたくなったら、置き換えずに新しい ID を足して古い方を廃止扱いにする。
- Zod スキーマを型と検証の定義元にして、ファイル検証・DB テーブル・API の型をそこから出す。
- 園地ごとの ON/OFF は、ルール本体の `enabled` ではなく運用設定として DB に持たせる想定。`enabled` は既定値の意味。
- 変更履歴のテーブルは、使わなくても設計に含めておく（あとから足すと既存データとの整合が面倒）。
- 検証で見る参照: diseaseId、when 内の var（scalar のみ）、stage の値、candidateFrac（文字列であること）、sourceIds、evaluator.name、fracCode。
- YAML の落とし穴: FRAC コード `21` は引用符なしだと数値になる。`"21"` と書く。

**FRAC の表（FRAC Code List 2026）**
- これは作用機構グループと有効成分の対応表で、日本の登録商品や使用基準は載っていない。商品データは別に作る（FAMIC で登録番号を確認できたものだけ入れる）。
- frac.yaml は90グループ、activeIngredients.yaml は254成分。旧コード→新コードは frac_reclassified.yaml（8件）。
- 前回レポートの有効成分22件の FRAC コードは、PDF と全部一致した。ただし石灰硫黄合剤だけは PDF に載っておらず、M2 かどうかは未確認。
- レポートの「高リスク系統（11・7・9・12・1・40・49）」という一括りは不正確。FRAC の記載は 1・11 が high、7・2 が medium〜high、9・3 が medium、12・40・27 が low〜medium。49・21 は medium〜high だが「想定値」。耐性管理の判断はこの値を基準に直す。
- CAA（40）はブドウべと病菌で耐性が知られていて、グループ内の全メンバーが交差耐性。レーバス（マンジプロパミド）、オロンディスウルトラ（＋マンジプロパミド）、ベトファイター（ベンチアバリカルブ）は、回数を数えるときに同じグループとして扱う。
- QoI（11）は G143A 変異株に対して全メンバーが交差耐性。国内のべと病では耐性菌が広がっているので、べと病には既定で「非推奨」扱いにする。
- 灰色かび病では 2（ジカルボキシイミド）で耐性が一般的、29（フルアジナム）は日本で耐性が主張されている、と PDF に書いてある。
- コード表記: 公式は `M 01`、既存データは `M1`（ゼロ埋めなし）。`label` に公式表記を入れて逃げている。揃えるなら一括置換。
- 商用利用は FRAC の事前許可が必要（教育目的は不要）。プロコン・Dコンは問題ないが、事業化するなら確認。
